## Stoff: Skriptsprachen, Bibliotheken und Frameworks; Programmiersprache auswählen

Ziel: Skriptsprachen, Bibliotheken und Frameworks einordnen, Sprachen für dynamische Webinhalte nennen und eine Sprachwahl begründen.

Das muss ich können:

### K1 – Skriptsprachen und Beispiele (Stufe 2 Verstehen)
Du kannst erklären, was eine Skriptsprache ist, und Beispiele nennen, etwa Shell-Skript.

Erklärung:
Eine Skriptsprache wird meist **interpretiert** und eignet sich für **kurze Programme ohne eigenen Übersetzungsschritt** – oft zum **Automatisieren** von Aufgaben.
Beispiele:
- **Shell-Skript** (Bash) unter Linux
- **PowerShell** unter Windows
- Python, JavaScript, PHP
Typischer Einsatz: jeden Abend automatisch Dateien sichern oder Benutzerkonten anlegen.

### K2 – Bibliothek gegenüber Framework (Stufe 2 Verstehen)
Du kannst Bibliothek und Framework unterscheiden: Eine Bibliothek rufst du auf; ein Framework gibt den Rahmen vor, in den du deinen Code einfügst.

Erklärung:
- **Bibliothek:** eine Sammlung fertiger Funktionen oder Klassen, die **dein Code aufruft**. Den Ablauf bestimmst du.
- **Framework:** ein Programmgerüst, das **Aufbau und Ablauf vorgibt**. Du fügst deinen Code an vorgesehenen Stellen ein, und **das Framework ruft ihn auf**.
Merkhilfe: Die Bibliothek rufst du, das Framework ruft dich.

### K3 – Statische und dynamische Webseiten (Stufe 2 Verstehen)
Du kannst statische und dynamische Webseiten unterscheiden: fertige, unveränderte Inhalte gegenüber Inhalten, die beim Aufruf erzeugt werden.

Erklärung:
- **Statische Webseite:** fertiger Inhalt, **bei jedem Aufruf gleich** – z. B. das Impressum als HTML-Datei.
- **Dynamische Webseite:** Der Inhalt wird **beim Aufruf erzeugt**, z. B. aus einer Datenbank oder aus Eingaben – z. B. die Trefferliste einer Shopsuche.

### K4 – Sprachen für dynamische Webinhalte (Stufe 1 Wiedergeben)
Du kannst Programmiersprachen für dynamische Webinhalte nennen, zum Beispiel JavaScript, PHP, Python; HTML und CSS zählen nicht als Programmiersprachen.

Erklärung:
- **JavaScript**
- **PHP**
- **Python**
- auch Java, C# oder Ruby
**HTML** (Struktur) und **CSS** (Gestaltung) zählen **nicht** als Programmiersprachen – sie haben keine Kontrollstrukturen wie Verzweigungen oder Schleifen.

### K5 – Kriterien für die Wahl einer Programmiersprache (Stufe 4 Beurteilen)
Du kannst ein Kriterium für die Wahl einer Programmiersprache begründen, zum Beispiel Eignung für die Aufgabe, Kenntnisse im Team, verfügbare Frameworks.

Erklärung:
Mögliche Kriterien – begründe, warum eines für die Situation wichtig ist:
- **Eignung für die Aufgabe:** z. B. JavaScript für Abläufe im Browser.
- **Kenntnisse im Team:** keine Einarbeitung nötig, weniger Fehler, die Wartung ist gesichert.
- **Verfügbare Frameworks und Bibliotheken:** man muss nicht alles selbst schreiben.
- Zielplattform, Geschwindigkeit, Kosten, Verbreitung und Weiterentwicklung (wird die Sprache weiter gepflegt?).
Beispiel: „Python, weil das Team es bereits beherrscht und es für Automatisierungsaufgaben viele fertige Bibliotheken gibt.“

### K6 – Programmierschnittstelle (API): Zweck und Nutzen (Stufe 2 Verstehen)
Du kannst erklären, was eine Programmierschnittstelle (API) ist: die festgelegten Funktionen und Klassen, über die dein Programm eine Bibliothek, ein Framework oder einen Dienst nutzt, ohne dessen Inneres kennen zu müssen.

Erklärung:
Eine Bibliothek will genutzt werden, ohne dass jeder ihren Code lesen muss. Dafür legt sie eine **API** fest.
- Die API beschreibt, **welche Funktionen und Klassen** es gibt, welche **Parameter** sie erwarten und was sie **zurückgeben**.
- Wie die Bibliothek intern arbeitet, bleibt verborgen und kann sich ändern, solange die API gleich bleibt.
- Jede Bibliothek und jedes Framework hat eine solche Schnittstelle; auch Webdienste bieten APIs an.
Beispiel: Du rufst `datumFormatieren(heute, "TT.MM.JJJJ")` aus einer Bibliothek auf und bekommst "16.10.2026" zurück – wie die Umrechnung intern geschieht, musst du nicht wissen.

### K7 – Clientseitige und serverseitige Skripte (Stufe 2 Verstehen)
Du kannst clientseitige und serverseitige Skripte unterscheiden: Ein clientseitiges Skript (zum Beispiel JavaScript) wird im Browser des Nutzers ausgeführt, ein serverseitiges (zum Beispiel PHP) auf dem Webserver, der nur das fertige Ergebnis, etwa eine HTML-Seite, an den Browser schickt.

Erklärung:
Dynamische Webseiten entstehen an zwei Orten.
- **Serverseitig:** Das Skript läuft auf dem **Webserver**, holt z. B. Daten aus einer Datenbank und erzeugt daraus HTML. Der Browser sieht nur das Ergebnis, nie den Skriptcode. Typisch: PHP, auch Python; Grundlage vieler CMS und Webshops.
- **Clientseitig:** Das Skript wird mit der Seite ausgeliefert und läuft **im Browser** des Nutzers, ohne vorher übersetzt zu werden. Typisch: JavaScript, z. B. um eine Eingabe sofort zu prüfen oder ein Menü aufzuklappen.
Beispiel Webshop: Die Artikelliste erzeugt der Server, die Prüfung „Menge muss größer als 0 sein“ beim Tippen übernimmt der Browser.

### K8 – Import von Bibliotheksmodulen (Stufe 2 Verstehen)
Du kannst eine Bibliothek (ein Modul) einbinden, um ihre Funktionen zu nutzen: vor der Nutzung, meist am Dateianfang, importieren (import in Python, #include in der Arduino-IDE) und über den Modulnamen aufrufen (z. B. math.sin(x)); eingebaute Funktionen wie print oder len brauchen keinen Import.

Erklärung:
Funktionen aus Bibliotheksmodulen werden vor der Nutzung importiert, meist am Anfang der Datei, und dann über den Modulnamen aufgerufen (z. B. math.sin(x)); eingebaute Funktionen wie print oder len stehen ohne Import bereit.

**Kerngedanken:**
- Es gibt keine beste Programmiersprache, nur eine, die zur Lage passt. Ein Kriterium zählt erst mit dem Satz, warum es in dieser Lage wichtig ist.
- Die Zielplattform kann alle anderen Kriterien aushebeln: Im Browser läuft von sich aus JavaScript, da nützen Kenntnisse des Teams in einer anderen Sprache nichts.
- Die API ist nicht die Bibliothek selbst, sondern deren festgelegte Außenseite. Ändert sie sich, etwa durch einen neuen Pflichtparameter, muss der aufrufende Code angepasst werden.
- Clientseitiger Code ist im Seitenquelltext sichtbar, weil er im Browser des Besuchers laufen muss.

**Typische Missverständnisse:**
- Viele denken, dynamisch heiße bewegt oder animiert. Richtig ist: Entscheidend ist, ob der Inhalt erst beim Aufruf erzeugt wird; eine Animation kann in einer festen Datei stehen.
- Viele denken, ein Framework sei eine große Bibliothek. Richtig ist: Der Unterschied liegt nicht in der Größe, sondern darin, wer wen aufruft.

**Fachwörter:**
- Skriptsprache: meist interpretiert, ohne eigenen Übersetzungsschritt
- Bibliothek: fertige Funktionen, die der eigene Code aufruft
- Framework: Programmgerüst, das den eigenen Code aufruft
- API: festgelegte Funktionen, Parameter und Rückgaben
**So fragt die IHK:**
- Drei echte Teilaufgaben, alle ohne Material, je 3 Punkte.
- Sprachwahl (2024H): ein allgemeingültiges Auswahlkriterium nennen und kurz begründen, etwa drei Zeilen. Gezählt werden zum Beispiel Anforderungen des Projekts, Erfahrung der Entwickler, verfügbare Tools und Frameworks, Zukunftsperspektive der Sprache. Das Kriterium allein reicht nicht.
- Dynamische Website (2025F): den Unterschied zur statischen erläutern – Inhalte zur Laufzeit erzeugt, abhängig von Benutzerinteraktion oder anderen Parametern.
- Sprachen (2025F): drei Programmiersprachen für dynamische Webinhalte nennen, je 1 Punkt; auch Ruby zählt, HTML und CSS sind ausdrücklich ausgeschlossen.
- Zu den übrigen Aussagen gibt es keine echte Aufgabe.

**Fallen:**
- Teil A: Zur dynamischen Webseite nur „ändert sich“ schreiben, ohne „wird beim Aufruf erzeugt“.
- Teil A: SQL als Programmiersprache für dynamische Webinhalte nennen. SQL ist eine Abfragesprache für die Datenbank; die Seite erzeugt ein Skript (z. B. PHP), das SQL-Abfragen nur an die Datenbank schickt.
- Teil A: „Client“ ist der Browser des Besuchers, kein Rechner beim Anbieter.
- Teil A: Einen Datenbankzugriff als clientseitig einordnen oder nur zuordnen, ohne zu sagen, wo das Skript läuft und was im Browser ankommt.
- Teil A: Zu Skriptsprachen nur Beispiele aufzählen, ohne die Merkmale, oder „Skript“ für unwichtig halten – Python und PHP tragen ganze Webanwendungen.
- Teil B: Die API nur als „Verbindung“ beschreiben, ohne Funktionen, Parameter und Rückgaben.
- Teil B: Fehlt der Import, bricht ein Python-Programm erst an der Zeile ab, die das Modul benutzt; die Zeilen davor laufen noch.
- Teil B: „Weil sie modern ist“ oder „die beste“ ist kein Kriterium; auch Geschwindigkeit ist selten das wichtigste.
- Teil B: Beim Beurteilen einer Sprachwahl das Gegenargument weglassen.
